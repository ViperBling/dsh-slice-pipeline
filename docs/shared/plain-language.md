# 产出文档语言规范（写给人看）

> 适用范围：讨论、设计、审查、修复等阶段产出的给人看的文本——主计划决策与问题、brief、审查 findings、fix 记录、薄文档、审查报告。
> 由各阶段 prompt 通过宿主注入的 `plainLanguagePath` 引用；机器字段名、枚举值与 JSON 结构一律不变，只约束说明文字与叙述。

## 1. 读者假设

- 读者是**没参加本次对话的同事**（或三个月后的自己）：不依赖上文，不假设读者知道内部流程词。
- **先结论后依据**：每段第一句说结论/会发生什么，再给依据。
- 一段只讲一件事；能用短句就不用长句；能用具体名词就不用抽象代词。

## 2. 术语与措辞

- 技术术语首次出现用一句中文解释，例如「环形缓冲（ring buffer：固定大小的循环队列，写满后覆盖最旧数据）」。
- 不用内部流程黑话。必须用时在括号里解释一次：盲审（先不看设计、只按改动审一遍）、对齐（拿设计意图复核上一轮结论）、门禁（不满足就阻止继续的硬校验）、兜底（失败时的退化路径）、锚定（先看到某个说法后被它带偏）、拓扑序（按依赖先后排列）、delta（本轮相对上一轮的改动）、两段式（先审、再拿设计复核的两个阶段）。
- 禁止空话：「视情况」「适当」「可能」「建议优化」。要写清什么条件、什么影响、怎么判断。

## 3. findings（审查意见）：现象 → 影响 → 建议

每条按三段写，字段名不变：

- **现象**（`issue`）：什么输入/操作/条件下会发生什么；有代码位置就带上。
- **影响**：谁会受影响、严重程度（`severity` 的 🔴/🟡/🟢 已表达分级，文字里再写一句后果）。
- **建议**（`fix`）：改哪个文件/函数、怎么改；不确定就写「需要确认 X」，不要给模糊建议。
- **证据**（`evidence`）：实际代码片段或命令输出；没有证据的判断不写进结论。

## 4. 决策与问题

- `decisions[]` 每条：做什么、为什么、影响谁、不做什么（`topic`/`decision`/`reason` 字段不变）。
- `openQuestions[]`：写成能用是/否或具体取值回答的问题，并附默认建议。
- brief 的 `architecture`/`details`：先说方案结论，再列 `file:line`、禁改区、验证命令；不复述流程术语。

## 5. 交付文档（薄文档 / 审查报告 / fix 记录）

- 标题与章节用大白话（「做了什么」「怎么验证」「没做什么」），不写内部阶段名。
- 验证记录写命令 + 退出码 + 关键输出，不写「已验证」。
- 结论与证据分开；不写自评，不堆过程黑话。

## 6. 不改变的东西

- 机器字段名、枚举值、JSON 结构一律不变。
- 技术精度不能丢：具体数值、类型、路径、错误码必须保留，不能为了顺口改成模糊说法。
- 与代码/规范原文冲突时，以原文为准并注明出处（文件 + 行号/小节）。
