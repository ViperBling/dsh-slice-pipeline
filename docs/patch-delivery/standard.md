# Slice Pipeline 补丁交付规范

> 适用范围：写代码、产出或修复 patch、写薄文档、交付三件套；由 `slice-patch-delivery` Skill 加载。
> 规范内容直接在本文件中维护；验证与回退交给[工作区恢复规范](../workspace-recovery/standard.md)。

## 1. Diff 的唯一事实源与落盘顺序

- **唯一事实源是 raw git diff/patch 文件（`*.patch` / `*.diff`）**，不是转写进 Markdown 的"Diff 文档"。Scratch 内 `git diff` 的输出原样保存，机器可直接 `git apply --check` 验证、`git apply` 落盘。
- **patch 内文件段顺序 = 依赖拓扑序，无条件强制**（用户 2026-08-17 起多次要求，2026-10-21 明确「严格执行」）。即使整包 `git apply` 对顺序不敏感也必须排序：人工逐段落盘、按段审查、按段回滚都以段序为前提。**排序只在文件段层面进行，不得改写任何段内的 hunk 内容。**
  - **头文件（`.h` / `.hpp` / `.inl`）必须排在其对应 `.cpp` / `.c` 之前**；
  - 整体顺序：**先声明（头文件） → 再实现（.cpp） → 最后使用方**；被依赖方先于依赖方；
  - 同一文件内的新增声明必须位于其首次使用点之前；
  - build wiring（`CMakeLists.txt` / `*.cmake`）与测试（`Tests/`）排在代码段之后；
  - 纯重命名（`git mv`、0 hunk）单独成段置于最前；
  - 若某 .cpp 依赖的声明在同一次 Diff 的某个头文件中新增，该头文件必须先于该 .cpp 出现，否则按序落盘后编译不过。
- **段序自证（每次交付前必做，三条缺一不可）**：
  1. **只换顺序、不改内容**：按段切分并重排后，逐段 SHA256 的**多重集必须与重排前完全一致**（对排序后取 SHA256 集合比对即可）；
  2. **可落盘**：`git apply --check <重排后 patch>`（干净基线）与 `git apply --check --reverse <重排后 patch>`（已应用树）均 exit 0；
  3. **顺序正确**：`git apply --numstat <patch> | cut -f3` 打印的实际段序与预期拓扑序逐行一致，且每一个 `.h/.hpp` 都出现在其同名 `.cpp` 之前。
- 违反段序 = 机械预检不通过，**不得进入 AI 审查、不得交付**。
- 薄文档只引用 patch 的文件路径 / 行号 / hunk 数，**不复制完整 diff**。仅在用户明确要求"贴进文档"的一次性小任务中才内嵌 diff，内嵌时同样遵守上述顺序。

## 2. 最终 patch 的代码放置与 include 顺序（用户硬要求）

> 适用：实现 / 修复阶段往 patch 里写代码时；同时是机械预检与代码审查的判据。**违反任一条 = 预检不通过，回到实现方重做，不得交付。**
> 只约束本片新增 / 修改的代码，不要求"顺手"重排未涉及的既有代码。项目 `AGENTS.md` / `CLAUDE.md` 有更具体约定时项目优先；项目没写到的按本节执行，本节优先于实现者的个人习惯。

### 2.1 类内内嵌类型先声明，新增项按字典序

- class / struct 内嵌的 `public` / `private` 的 `struct` / `class` / `enum` / `enum class` / `using` 别名，**必须集中声明在类中首次使用它们之前**（通常在该类的类型区），不得零散插在函数声明旁边、访问区尾部或类末。
- **先声明后使用**：内嵌类型 → 使用它的成员变量与函数声明。没有依赖关系时，**本片新增 / 修改的**内嵌类型按**字典序**排列（按符号名比较：ASCII 大小写不敏感升序，等值再按原拼写比较；项目已有更严格的排序惯例时随项目惯例）。
- **不重排既有行**：既有块本就不是字典序时，不为满足本条重排既有行——把新增项插在同语义族的最后一个既有项之后，只保证本片新增项彼此按字典序；有依赖的（A 作为 B 的字段类型）被依赖方排在依赖方之前。
- 访问区跟随既有布局：该 public 的仍放 `public:`、该 private 的仍放 `private:`；不新增访问区、不重排既有区块。

### 2.2 新增函数 / 变量按原有分块放置

- 新增成员函数、成员变量、文件级函数与变量，放进文件中**语义对应的已有分块**（构造 / 析构与生命周期、初始化、访问器、状态更新、内部工具、静态辅助……），在该块内按下面的插入点与排序规则就位；不得"就近找空行"追加，也不得新开一个只为塞新增项的杂块。
- 同一块内本片新增项之间无依赖关系时按字典序；插入点取语义同族的既有项之后（既有块非字典序时同样不重排既有行）。确实属于新概念才新开分块，并在薄文档「关键设计说明」写明理由。
- 新建文件 / 新类没有既有分块可依时，按 2.1 的声明顺序与项目同类文件的通行布局自建分块，并在薄文档「关键设计说明」写明布局依据。
- 成员变量与函数不混放：变量跟随项目既有的成员区布局，不散落到函数声明之间。

### 2.3 函数实现顺序 = 声明顺序

- `.cpp` / `.cc` 中成员函数定义的顺序，必须与头文件中的声明顺序一致；静态函数、自由函数同理（先声明的先实现）。同一类 / 同一模块的实现连续排布，不得把同类函数散落到互不相邻的段落。
- 例外仅限语言规则强制的：`inline` / 模板 / 显式特化等必须放头文件或按编译需求就近实现的，不计违规；拆分到多个 `.cpp` 的辅助实现按"单个文件内声明块连续"检查。

### 2.4 include 顺序

1. **本类头文件在最上**：`Foo.cpp` 的第一行 include 就是 `#include "Foo.h"`（该实现文件自己的声明头），其后空一行。头文件不 include 自己。
2. **三块分组，块间空行**：① 项目内头文件（同仓库 / 同模块）；② 第三方头文件（外部库 / SDK；vendored 进仓库的第三方随项目既有惯例归入本块）；③ 系统头文件（C/C++ 标准库与平台头）。
3. **块内字典序**：块内无特殊顺序要求时按文件路径字典序升序。比较口径：分隔符统一为 `/` 后的路径文本，ASCII 大小写不敏感比较，等值再按原拼写；`../` 按原样参与比较；同前缀按完整路径比较。
   - 例外：① 确需先定义宏才能 include 的头、必须置于块末的兼容 / inline 头，保留在正确位置；② 预编译头（MSVC `/Yu` 的 `pch.h`、UE 的 `CoreMinimal.h` 等）按项目惯例置顶。例外的都要在薄文档说明原因。
- **整理范围**：只整理本片确实要插入新 include 的那个块——该块内既有行保持原样，新增行按上述规则插入（既有块非字典序时，插在同前缀 / 同族的最后一个既有项之后，只保证新增行彼此有序，与 2.1 口径一致）；整块重排既有 include 仅在用户明确要求时进行，并在薄文档说明。与本片无关的 include 一律不动。

### 2.5 自检、预检与审查口径

- **实现方**：生成 patch 前按 2.1–2.4 逐条自检，在 `verifyResult` 写一句结论（如 `style: 2.1–2.4 已自检`）；无法满足的写明确切条目、`file:line` 与原因，不得沉默放过。
- **机械预检**：按本节逐条核验 patch 的新增 / 修改部分（内嵌类型是否在首次使用前、`.cpp` 实现顺序与头文件声明顺序是否一致、include 是否为本类头文件 + 三块 + 块内字典序）；不通过即不进入 AI 审查。
- **代码审查**：十维清单第 5 条按本节逐条核验，违规按 🟡 报（引发编译 / 语义问题的按实际严重度报）。审查规范里的"忽略命名与风格"指忽略个人命名口味与格式偏好，**不含**本节明列的放置顺序与 include 顺序。
- **分级不软化门禁**：生成阶段违反本节 = 预检不通过、不得交付；审查阶段发现按 🟡 报，但**本节项必须修正或由用户明确豁免**后才能闭环，不得以审查规范里"🟡 可写接受理由"关闭——本节是用户硬要求，不适用那条兜底。

## 3. 交付流程

**默认交付物 = `<项目根目录>/AIOut/<任务名>/` 下的三件套，不是改好的代码文件，也不是大而全的 Markdown Diff 文档。** 除非用户明确要求"直接修改 / 落盘到仓库"，否则按下述流程执行：

0. **先产出 Slice brief（主会话写，不派 agent）**：按[规划规范「4. Slice brief」](../planning/standard.md)执行；brief 从 `design` 输出的 `research` 提炼，写入 `plan.json` 的 `slices[i].brief`（含 `file:line` 与验证命令），不再单独起调研。多 Slice 任务的计划评审（`planReview`）与 brief 审查（`briefReview`）已归档，不阻塞实现。
1. **在 Scratch 实现完整代码**：依据[审查运行时规范「十维审查清单」](../review/review-standard.md) / [审查派发规范「设计原则清单」](../review/review-dispatch.md) 产出代码；文件段序为依赖拓扑序（头文件先于对应 .cpp、wiring/测试靠后，见本文「1. Diff 的唯一事实源与落盘顺序」）；代码放置与 include 顺序逐条满足本文「2. 最终 patch 的代码放置与 include 顺序」；只含源码变更，不含构建产物。禁止直接在用户工作区改码。
2. **选验证场地**：按[工作区恢复规范「1. 验证场地与基线快照」](../workspace-recovery/standard.md)执行。
3. **编译验证**：运行项目真实编译/构建命令（或覆盖改动文件的最小构建目标），以**退出码 0** 判定通过，并记录命令与关键输出。单目标/单 TU 的快速做法与负向注入取证见[审查派发规范「验证类证据的最小成本路径」](../review/review-dispatch.md)。未通过则修复后回到第 2 步重新验证，直到通过；遇到无法解决的阻塞时停止并如实报告，不得声称"可编译"。当前环境无法编译时，必须如实标注"未验证编译"。
4. **回退（仅原仓库验证时执行）**：按[工作区恢复规范「2. 回退到基线」](../workspace-recovery/standard.md)执行。
5. **生成 raw patch 并过机械预检**：
   ```bash
   git -C <scratch> add -N <新增文件>          # 让新增文件进入 diff
   git -C <scratch> diff --check                # 空白/冲突标记检查
   git -C <scratch> diff > <任务名>.patch
   git -C <scratch> apply --check --reverse <任务名>.patch  # patch 与工作树一致
   # 目标仓库落盘前：
   git -C <repo> apply --check <任务名>.patch   # 必须干净通过
   ```
   机械预检项：目标仓库 `git apply --check` 干净、patch 与工作树一致、文件顺序满足本文「1. Diff 的唯一事实源与落盘顺序」、**代码放置与 include 顺序满足本文「2. 最终 patch 的代码放置与 include 顺序」**、无构建产物、R8/R10 等脚本门禁、验证记录与命令一致。**预检不过不进 AI 审查。**
6. **审查与修复闭环**：按[审查派发规范「审查派发」](../review/review-dispatch.md)派发审查，审查输入 = raw patch + brief（`plan.json` 的 `slices[i].brief`，或兼容的 briefFile）+ 薄文档元数据 + codegraph 项目路径；**不附自评表与历史修订**。修复闭环按[审查派发规范「审查-修复闭环」](../review/review-dispatch.md)，修复后必须重新编译并重新生成 patch。
7. **写回三件套**：
   - `<任务名>.patch`：最终编译通过、回归审查通过的那一版 raw patch，逐文件完整，不得改写；
   - `<任务名>.md`：按[薄文档模板](thin-document-template.md)写的薄文档；
   - `<任务名>-review.md`：审查报告与逐条处置（放 `reviews/` 或任务目录，见[审查派发规范「派发提示词」](../review/review-dispatch.md)）。
   - 旧版本移入 `archive/`，活文档不留历史附录；对话回复中只给文件路径与摘要，不贴全文（除非用户要求）。
8. **闭环立即同步**：更新主计划决策日志与 Slice 状态、项目索引（如 `AIOut/*/00_INDEX.md`）、版本号；**不得留到"用户落盘时手工同步"**。文件命名默认 `AIOut/<任务名>/`；一次性小任务允许单文件 `AIOut/<任务简述>.md`，但仍优先三件套。
9. **例外**：用户明确说"直接改 / 直接落盘"时，跳过第 4 步回退，保留已修改文件，但仍须第 3 步编译通过后才算交付；此时默认不写第 7 步文档（用户要求则写）。
