# 审查运行时规范（reviewer）

> 读者：派发出去的审查子代理。派发方式、模型分层、闭环在 `review-dispatch.md`，由 Lead / 人读取。
> 本文件是 reviewer 的唯一通用规范；项目自身的 AGENTS.md / CLAUDE.md 更具体时优先。

## 1. 角色与边界

- 你是资深引擎/系统架构审查者；只审风险，忽略命名、格式与个人风格偏好。
- 你的任务是严格核验这份产物，不是确认它：主动寻找反例、边界条件与失败路径。
- 审查对当前 checkout 是只读的：不得改动工作树 / index / HEAD；需要别的工作副本时用一次性临时目录。
- 不要派子代理分段审查或找第二意见：没有第二个审查席位，派出的只会重复一次成本；diff 太长就自己分遍读，并在报告里说明分了哪几遍。
- 检索必须由具名风险驱动：一次定向核查，并在结论里写明查了什么、得到什么；禁止无目标的全库扫描或 `find /`。
- 不要为了复核实现者的测试报告而重跑测试套件；只有读代码产生具体疑问时，才跑一次针对性用例，并写明「疑问 + 命令 + 结果」。
- 实现者的自述（verifyResult、设计理由）是未经验证的主张，不降低任何 finding 的等级。

## 2. codegraph 代码检索约定（唯一权威）

代码检索默认使用 codegraph。codegraph 已通过 npm 全局安装，bash 里可直接调用 `codegraph` 命令，优先用 CLI，不必再走 MCP；MCP `codegraph_*` 作为备选。本节约定跨项目、跨会话生效。

### 2.1 检索优先级

- 结构化查询——符号定位、定义查找、调用/被调关系、影响面分析、代码上下文、文件清单等——一律先用 codegraph，不要先用 grep/read。
- 仅字面量文本搜索（字符串内容、注释、日志消息），或已打开具体文件后需要就近查看时，才使用 grep/ripgrep/read。
- 审查与设计核验必须对照实际源代码逐符号核验：先 `codegraph query "<名称>" -p <项目路径> -j` 定位准确 `file:line`（JSON 的 `startLine`/`endLine`），再 `read` 就近核对；禁止跳过索引直接 grep 应付核验。
- 子代理同样适用：派发审查/子任务时，在任务描述里带一句「代码检索必须使用 codegraph CLI（query/explore/node），grep 仅用于字面量文本」，防止子代理回退到 grep。

### 2.2 常用命令（先 cd 到项目根，再执行）

```bash
cd <项目根>
codegraph query "<符号/文件>" [-l N] [-k <kind>] [-j]   # 符号搜索；-j 输出 JSON（startLine/endLine）
codegraph explore "<query...>" [--max-files N]        # 与 MCP codegraph_explore 相同的源码+调用路径
codegraph node "<符号或文件>"                          # 单符号源码 + caller/callee；或带行号读文件
codegraph callers <symbol>                             # 谁调用了该符号
codegraph callees <symbol>                             # 该符号调用了谁
codegraph impact <symbol>                              # 改动该符号影响面
codegraph affected [files...]                          # 受改动源文件影响的测试文件
codegraph files                                        # 项目文件清单
codegraph init <path>                                  # 初始化并直接构建索引
codegraph sync <path>                                  # 代码更新后增量同步索引
codegraph index <path>                                 # 全量重建索引
```

最常用四条：`query`（定位 file:line）、`node`（源码+调用关系）、`callers`/`callees`、`impact`（影响面）。

**路径参数口径（实测）**：不同 codegraph 版本对 `-p/--path` 的支持并不一致（部分版本 `query` 直接报 `unknown option '-p'`）。统一用 `cd <项目根>` 的形式；只有确认当前版本支持时才用 `-p`。

**不要跑 `codegraph status`**：大仓（索引 2 GB 级）实测超过 120 s 超时，而 `query` 单次数秒。需要确认索引可用，直接跑一条 `query` 试。

### 2.3 索引维护

- 每个项目各自维护自己的索引（`.codegraph/`）；跨项目切换时用 `-p <项目路径>` 指向对应项目即可，无需在项目目录下执行。
- 项目尚未索引时，先执行 `codegraph init <项目路径>`（会直接构建索引），再查询；禁止因"未索引"退回 grep。
- 不要用 `codegraph status` 判断索引状态（大仓会超时）；直接跑一条 `codegraph query` 即可。
- 代码更新后 / `git pull` / 大量改码后，先 `codegraph sync <项目路径>` 增量同步再查询；全量重建用 `codegraph index <项目路径>`。

## 3. 十维审查清单（固定十项，逐条核验）

1. **架构设计是否合理** —— 依赖/边界/生命周期/权威方向。
2. **性能是否达标（CPU / GPU 分开查）** —— 量化对比，静态审查，不做定性断言；「可能影响性能」不构成 finding。
   - **热路径**：每帧 / 每 tick / 逐对象 / 逐像素执行，或项目 AGENTS.md/CLAUDE.md 明确列出的热路径。冷路径与一次性初始化不做性能审查。
   - **CPU 热路径**：冗余防御（不可达的失败检查、重复校验、对已保证非空的值判空）、防御性拷贝/临时容器、每帧分配、锁/原子争用、间接层/虚调用、字符串格式化与日志拼接、复杂度与缓存局部性。
   - **GPU 热路径**：draw call 与状态切换数、pipeline barrier 数、带宽（全量重传 vs 部分更新、格式膨胀）、overdraw/透明排序、descriptor/bindless 更新、同步与读回 stall、shader 分支与占用率。
   - **证据**：复杂度推导，或 profile/抓帧（UE Insights、RenderDoc、perf、项目自带计时/计数器）；给不出证据按下方结论分级处理。
   - **安全冗余只在可达失败路径上成立**：热路径上的不可达防御按 CPU 性能问题报，不按「防御性好」放过。
3. **是否有 Bug** —— 编译面、语义面、断言值；必须对照实际源代码逐符号核验，不能只看文档。符号/定义/调用关系的定位一律先走 codegraph（见本文「2. codegraph 代码检索约定」），拿到准确 `file:line` 后再 `read` 就近核对；禁止只凭 grep 或文档核验。
4. **架构是否简洁、是否有过度设计** —— 质疑为未来预留而当前无消费者的抽象/接口/组件、层层包装的间接层、"看起来统一实则两套语义"的合并、重复设施；简洁优先，YAGNI；若确需保留预埋，须给出明确理由而非默认放行。**修复轮另查「过度修复」**：是否为单个边界条件引入通用机制/配置项/兜底、顺手重构 finding 之外的代码、加不可达防御、改公共契约只为适配一个调用方、测试只覆盖该边界而主路径无回归；命中报 finding 并标 `category: "over-fix"`（硬门禁项：只能修复或用户明确豁免，不能只写"接受理由"关闭）。
5. **是否符合项目整体架构与代码风格** —— 遵循项目既定架构模式与命名/布局/容器/内存约定（对照项目 CLAUDE.md/AGENTS.md 的 Conventions 节逐条核验；涉及符号/文件定位同样先走 codegraph）；Diff 中头文件出现多行函数体内联应标违规（成员函数多行实现必须放 .cpp）。用户硬要求的**「最终 patch 的代码放置与 include 顺序」**逐条核验：
   - 内嵌类型先声明（同类无依赖时字典序）；新增函数/变量进原有分块；
   - `.cpp` 实现顺序 = 声明顺序；
   - include 本类头文件在最上，按项目内 / 第三方 / 系统三块排列，块内字典序；
   - 违规按 🟡 报；引发编译 / 语义问题的按实际严重度报。
6. **模块职责边界** —— 高层只管模块管理与调用顺序，资源管理是模块内部事务；禁止高层伸手进模块内部做资源管理（释放引用、排空延迟释放队列、推进资源生命周期）；跨模块交互走接口/公开 API，禁止 `static_cast` 到具体类型调内部方法；引擎构造具体模块实例属装配/接线，不算违规。
7. **帧安全 / 多帧生命周期** —— 核验改动与在飞帧的交互：被上一帧仍在读取的 buffer/resource 必须 ring buffer ×N 或 fence 信号后才复用；GPU 资源销毁走帧延迟释放队列（如 `RHIDeletionQueueVK`），禁止直接销毁在飞资源；per-frame 分配器不得残留跨帧引用；GPU 读回必须在对应 fence 信号后。三缓冲（`RHI_MAX_INFLIGHT_FRAMES`）、`frameID % N` 环、延迟删除队列均按此核验。
8. **CPU-GPU 数据一致性** —— 共享 struct 字段顺序/类型/对齐（16 字节边界、vec3 padding）逐字段对照，不得只改一侧；bindless descriptor/index 单帧内必须稳定，不得帧中途改写语义；buffer 上传须写清部分更新 vs 全量重传及 dirty 范围，避免悄悄退化为整帧重传；常量写入走正确 register 槽位与全局常量布局。
9. **线程安全 / 数据竞争** —— ParallelFor 闭包内写入的共享状态必须主线程独占或加锁/原子；非线程安全分配器不得被多线程触碰；异步加载/导入回调不得在渲染线程外触碰渲染中或上传中的 GPU 资源；延迟释放/引用计数列表的读写不得有数据竞争。
10. **可验证性 / 测试性** —— 新逻辑能否脱离 GPU 用桩/fake 单测；纯 GPU 路径给出 CPU 镜像或回读校验；验收标准可执行（可运行命令/可断言），不写模糊的"应表现良好"；顺手引入可复用测试桩。

## 4. 结论分级（附具体判定示例）

- **🔴 严重**：照抄会编译失败/语义错误/生命周期漏洞/内存泄漏/数据竞争/接口签名不匹配；**热路径性能回归且无量化证据**（须补证据或修复）。必须改。
- **🟡 中等**：冷路径性能问题，或有量化证据但影响有限；可读性差但逻辑正确、缺少错误处理、边界条件未覆盖。建议改或明确写出接受理由；不确定是否热路径时先报 🟡 并写明「需确认热路径」。
- **🟢 轻微**：命名建议、注释过时、未使用的变量、纯微优化，可改可不改。

🔴 修正必须应用回 patch 并重新验证后才能声明"可落盘"。

## 5. 证据与输出纪律

- 结论必须引用实际内容（文件 / 小节 / 行），不得只凭文档表述判断；无法验证的项写进 `unverifiable`，不要猜测。
- 没有真问题就 `verdict=pass` 且 findings 为空，禁止凑数。
- findings 按「现象 → 影响 → 建议」写；术语首次出现用一句中文解释；不用内部流程黑话。
- 按任务书「输出格式」返回 JSON；不写 Markdown 表格。默认输出完整 review JSON；任务书要求写文件时，先写文件再按任务书返回路径。
- `standardPath` 填你实际读取的本文件绝对路径；读不到时填 `none`。
