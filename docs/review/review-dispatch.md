# 审查派发与闭环规范（Lead / 人工）

> 读者：Lead 与人工派发审查的人。reviewer 只读 `review-standard.md`（运行时规范）。
> 本文件保留派发纪律、模型分层、工具与验证约定、设计原则和修复闭环。

## 1. 适用范围

- 用于决定“发什么、用哪个模型、怎么处理审查结论、怎么闭环”。
- 审查判据（十维清单、分级、codegraph、证据与输出纪律）在 `review-standard.md`，派发 reviewer 时让子代理读那一份。
- 项目自身的 AGENTS.md / CLAUDE.md 更具体时优先。

## 2. 审查派发（用户说「派发审查」/ 让 XX 做 review 时）

### 2.1 审查输入纪律（默认生效，直接节省 Token）

- **两段式顺序（默认生效）**：把「只发」拆成两步——先只发 patch 与实际代码做**盲审**，独立得出结论；再把 brief 的 architecture 层给同一会话做**对齐**复核，补出「偏离既定方案 / 越界改动 / 过度设计」，并撤回站不住的盲审项（写清与哪段实际代码/契约不符）。**顺序不可交换**：先看到 brief，越界与过度设计就失去判据。结论按来源标 `blind` / `alignment`。
- **审查包（逐阶段 review 自动生成）**：宿主把 patch 全文 + 薄文档 + 改动统计 + 本片范围/验收 + 机械预检结果打成 `<outDir>/reviews/<sliceId>-package-r<round>.md`，审查者**只 read 这一个文件**、不跑 `git` 命令、不无目标地爬库；包内上下文行就是改动视图。生成失败（patch 读不到等）时退回按路径读取，并在结论里说明。批处理 `slice` 仍按路径读取。
- **只发**：raw patch（`<任务名>.patch`）+ 本片 brief（`plan.json` 的 `slices[i].brief`，其 architecture 层只在**对齐阶段**给出）+ [薄文档模板](../patch-delivery/thin-document-template.md)的「1. 目标与范围」至「3. 关键设计说明」+ 主计划本 Slice 小节 + codegraph 项目路径。
- **不发**：R0-RN 自评、十维自评、A-F 自评、历史修订、旧版 diff、整份主计划、无关源码文件；自评会让审查模型锚定并浪费 Token。
- 单次审查规模上限：**≤ 60 hunks / ≤1200 增删行**；超过先拆 review focus（按模块或文件族），不要一个模型上下文硬啃超大 patch。先给审查模型 `git diff --stat` 概览。
- **拆分与汇总（超过上限时按此执行）**：
  1. 拆法：按模块 / 文件族切成 N 个 focus，每个 focus 单独派发一次审查（各自 ≤ 上限），并在派发说明里写清「本轮只看 <focus 范围>，其余文件不在本轮」。
  2. 报告：**最终只落一份** `AIOut/<任务名>/reviews/<任务名>-review-<YYYYMMDD>.md`；每个 focus 的结论作为该报告的一节，节标题写 focus 范围与涉及的 hunk 区间。
  3. 去重与冲突裁决：**由主会话负责**（不是审查模型）。同一问题被多个 focus 报出时合并为一条并标注「多 focus 共同命中」；两个 focus 结论冲突时，主会话按「引用实际代码核验」为准裁决，并在该条下写明裁决依据（文件+行号）。
  4. 分级汇总：合并后重新给出**全局** 🔴/🟡/🟢 计数，修复闭环按合并后的 🔴 清单执行；分 focus 的数字只作为附录。
  5. 修复后复审：只对修复 hunk 与受影响调用链做一次回归审查，不再按 focus 重审全量。
- 审查行号以 codegraph 实际源码 `file:line` 为准；先 `codegraph query/node` 定位，再 read 就近核对，不凭 patch 行号。
- **raw patch 的行号口径（本片新增符号查不到时必读）**：codegraph 索引是 **patch 前基线**，本片新增的符号/函数在索引里不存在，因此：
  1. 先在工作树外生成 **post-image 副本树**（把 patch 应用到临时副本，例如 `%TEMP%/<slice>-tree/`），保持与原仓相同的相对路径；
  2. 对副本树单独索引（`codegraph init <副本树>`）或在副本树内 `codegraph query`；
  3. 报告里的行号统一写 **post-image 副本树的 file:line**，并在报告开头注明「行号基准：post-image 副本 <路径>（基线 commit <sha>）」；
  4. 不可核实到具体行时写 `N/A` 并说明原因，禁止估算。

### 2.2 审查顺序（省人工时间）

1. **机械预检**（脚本 / 便宜模型）：`git apply --check`、**patch 文件段序 = 依赖拓扑序**（头文件先于对应 .cpp、wiring/测试靠后；顺序错即预检不通过，见[补丁交付规范「1. Diff 的唯一事实源与落盘顺序」](../patch-delivery/standard.md)）、**代码放置与 include 顺序**（按[补丁交付规范「2. 最终 patch 的代码放置与 include 顺序」](../patch-delivery/standard.md)逐条核验，属用户硬要求、不属个人风格）、编译 exit 0、ctest、`git diff --check`、R8/R10 门禁、patch 与文档一致性。预检不过不进入 AI 全量审查。
2. **AI 审查 raw patch**：首轮（round=1）全量两段式；复审（round>=2）默认**聚焦增量**——只审「上一轮 findings 逐条状态 + 修复 delta + delta 触及符号的调用链影响面」，材料不足或触发升级条件时自动回全量。均按审查运行时规范「十维审查清单」与本文设计原则。
3. **修复闭环**：本文「3.3 审查-修复闭环」；修复后重新编译 + 重新生成 patch。
4. **人工终审**：只读「审查处置表 + 未达验收项 + 接受的风险」这一页摘要；不再通读完整 diff。用户主动要求人工先通读时除外。

### 2.3 审查模型分层（默认，可按用户指定覆盖）

> 审查模型不在本规范中写死；以 Slice Pipeline 插件设置里的 `reviewer` 角色为准。需要更换审查模型时，改插件设置里的 `reviewer` 角色，不要改本文件。

| 风险档 | 判据 | 审查执行 |
| :--- | :--- | :--- |
| 高 | 帧/多帧生命周期、同步/fence、GPU 资源销毁、线程竞争、ABI/共享内存布局、核心热路径、跨模块接口 | 运行前将 `reviewer` 指向最强审查路由，再由该角色全量审查 |
| 中 | 多文件逻辑重构、错误路径、语义变化、无并发但涉及多个调用链 | 使用当前 `reviewer` 角色全量审查；出现 🔴 或存疑项时，由用户决定是否切换 `reviewer` 路由后重新复审相关文件 |
| 低 | 重命名、机械适配、独立缺陷、纯新增测试、门禁脚本 | 使用当前 `reviewer` 角色审查；不额外升级 |

- 用户明确要求"强模型审查"时，运行前把 `reviewer` 角色指向对应路由；本规范不写具体模型 ID。
- **计划/接口契约评审**（**归档，不启用**）：原为多 Slice 任务切片前的一次评审，2026-11-03 起与 `planReview` 一起归档；`design` 直接交用户确认。用户明确要求时仍可人工派发一次（报告落盘 `plan-review-<YYYYMMDD>.md`），但不再是进入实现的必要条件。代码审查与修复闭环不受影响。
- 二次回归审查聚焦修复 hunk + 受影响的调用链，使用 `reviewer` 角色；首次高风险的 Slice 如需更强模型，运行前切换 `reviewer` 路由。
- **effort 固定**：使用 `reviewer` 角色所选 provider 路由的 `reasoning` 默认值，不得在审查阶段为省 token 显式降档。需要不同 effort 时，配置同端点、不同 `reasoning` 的 provider 路由，再在插件设置里把 `reviewer` 指向对应路由。
- **派发执行**：workflow 的 `agent()` 当前不接受 per-role effort；模型与 effort 均由 `reviewer` 角色所选路由决定。主会话不要另行硬编码模型 ID。

### 2.4 派发提示词（角色设定与检索约定必须放最前面）

给审查 agent 的提示词**最前面**必须加上以下角色设定与检索约定，其后才是审查任务、patch 路径与薄文档路径：

**你是一个资深的引擎图形开发专家。你的核心职责是进行高价值的架构与逻辑审查，而非纠正代码风格。请忽略命名、格式、个人风格偏好，聚焦于十维审查清单中定义的关键风险点。**

**你的审查输出必须严格遵循以下表格格式：**

| 严重程度 | 文件 | 行号 | 问题描述 | 修复建议 |
| :--- | :--- | :--- | :--- | :--- |
| 🔴/🟡/🟢 | path/file.cpp | L42 | ... | ... |

**输出要求**：
- 每条问题占一行，按严重程度排序（🔴 在前，🟢 在后）；
- 行号必须精确到审查运行时规范「2. codegraph 代码检索约定」定位的实际行号，不得估算或留空；
- 问题描述须引用实际代码片段（上下各 1-2 行为限）佐证；
- 文字按[产出文档语言规范](../shared/plain-language.md)写：现象→影响→建议，术语首次出现解释，不用流程黑话；字段名不变；
- 无问题可报时，输出"未发现违反十维清单的问题"，不得强行凑数。

代码检索**必须**使用 codegraph CLI（`query`/`explore`/`node`/`callers`/`callees`/`impact`，见审查运行时规范「2. codegraph 代码检索约定」），grep 仅用于字面量文本；对照源码逐符号核验时先走 codegraph 定位 `file:line`。

- 该角色设定与审查运行时规范「十维审查清单」及本文设计原则叠加生效。
- **例外（用户硬要求，不属"风格"）**：[补丁交付规范「2. 最终 patch 的代码放置与 include 顺序」](../patch-delivery/standard.md)里的放置与 include 规则必须逐条核验并按 findings 报出；本条「忽略命名与风格」指忽略个人命名口味与格式偏好，不覆盖这些明列规则。
- 跨项目生效，用户无需每次重复；若某次用户明确说本次不加角色提示词，以当次指令为准。
- **派发审查子代理时三件套**：① 使用 Slice Pipeline 配置中的 `reviewer` 角色路由，不在本规范里写死模型；② 提示词开头加本节角色设定；③ 任务描述附一句「代码检索必须使用 codegraph CLI（query/explore/node/callers/callees/impact），grep 仅用于字面量文本」。三项直接照抄。
- **审查报告落盘**：默认写入 `<项目根目录>/AIOut/<任务名>/reviews/<任务名>-review-<YYYYMMDD>.md`；一次性任务写 `AIOut/reviews/<任务简述>-review-<YYYYMMDD>.md`。用户明确要求不落盘时除外。

### 2.5 工具权限与调用纪律

- 默认省略 sandbox_permissions / justification，不传无用字段，也不填 null；审批或提权以当前工具说明和实际权限模式为准。
- 该报错**不是命令失败**：提权判定在命令执行前完成，被拒时什么都没跑、无副作用。命中后按「去掉两个字段、原样重发一次」处理，**不得**改写成别的命令绕行，也不得在 `workspace-write` / `danger-full-access` 之间连环重试（只会白烧步骤与 token）。
- 只有确实收到 `[sandbox: file access denied under <mode> mode]`、且当前档位**确实窄于**目标档位时，才允许按本文「2.4 派发提示词」的角色约定做一次提权重试；当前档位已是 `danger-full-access` 时不存在合法提权目标，拒绝即为最终结果。
- 不把 approval: never 等同于完全访问。遇到策略拒绝，不换命令、工具或路径绕过；没有合法审批通道时停止并如实说明。
- 本机原因见[人工派发约定「工具能力与本机满档偏好」](../shared/dispatch-guide.md)。

### 2.6 验证类证据的最小成本路径（跨项目默认）

审查与修订阶段常需要**编译期反例**（证明某条 `static_assert` 真的会触发、证明某类型不满足某约束、证明改动前能编译而改动后不能）。默认按下列路径取证，**不要**在临时目录重建整棵树后手拼编译器命令行：

1. **用工程自带构建系统取真实命令行**，不凭记忆拼 `clang++` / `cl` 参数：
   - CMake + Ninja：`ninja -C <build> -t commands <obj 目标> | tail -1`；构建树里的 `compile_commands.json` 同样可用。
   - 其他：Cargo `cargo build -v`、MSBuild `/p:…`、Make `make -n`。
2. **单目标增量编译**：只把**那一个对象文件**当构建目标（如 `ninja -C <build> <dir>/Foo.cpp.obj`），秒级到十几秒出结果；不为一条断言跑全量构建。
3. **负向注入**：原地改一处（或临时加一条违规条目）→ 跑第 2 步 → 断言**退出码非 0** 且错误文本含预期断言/错误码 → `git checkout -- <文件>` 恢复。证据里同时贴退出码与错误行，**没有真的跑过不许写「实测」**。
4. **需要干净基线副本时用版本控制导出**：`git archive <sha> | tar -x -C <dir>`，不要拷贝整棵树再重新 configure。
5. **环境先决条件一次弄清**：MSVC 的 `cl.exe` 依赖 vcvars 设好的 `INCLUDE/LIB`，直接调用绝对路径会报 `C1083: cannot open include file: 'cstddef'`；Windows 下从 Git Bash 调 `cmd` 时**禁止内联长命令**（`cmd /c "a >nul && b"` 会被二次解析，典型症状是只打印 cmd 横幅、`ERRORLEVEL` 不生效），统一写临时 `.bat` 再 `cmd //c <路径>`，或改用 `pwsh -Command`。
6. **按最小手段估耗时**：十秒内能拿到的单目标编译证据，就不要走「整树 + 起进程」的路；确实需要运行环境时，先说明为什么静态推理与单目标编译不够。

## 3. 设计原则与执行纪律

### 3.1 设计原则清单（设计/审查判据）

**总纲：依赖朝抽象、单一职责、状态唯一、失败早报、可验证才交付。**

- **A. SOLID（类/接口级）**：单一职责（一个类一个改变理由）；开闭（对扩展开放、对修改封闭）；里氏替换；接口隔离（接口按调用方切分）；依赖倒置（高层低层都依赖抽象，依赖方向永远朝抽象，如 `RHI→Renderer→Core` 倒置 = 违反）。
- **B. 模块/架构级**：分层依赖方向单一（只允许上层依赖下层，`Framework/RHI` 不得引用 `Renderer/`、`Core/`）；稳定依赖 + 稳定抽象（稳定模块应抽象、不被不稳定模块依赖）；最少知识（Demeter）；高内聚低耦合；组合优于继承；清晰分层（UI/逻辑/数据/底层分离）；控制反转（组合根负责装配，被装配者不得反向 `GetEngineInstance()` 满天飞）；封装/信息隐藏（实现细节收在模块/类内、只暴露最小接口）；关注点分离（计时/日志/统计等横切逻辑用 RAII scope/宏插桩，不散落业务函数）。
- **C. 通用工程**：DRY（一处事实一处定义）；KISS/YAGNI（不为想象的需求加抽象/间接层，预留须给理由）；最小惊讶（命名准确）；Fail Fast（尽早失败、错误清晰、不静默吞错）；单一事实来源（状态/配置只在一处持有）；RAII 优先（成对 begin/end、acquire/release 绑定对象生命周期，析构自动收尾）；声明式优于命令式（表达「要什么」而非手写「怎么做」）；约定优于配置（前缀命名驱动聚合/发现，约定变更须同步消费者）；先验证再交付（patch 中的代码须经编译验证通过后才交付）。
- **D. 渲染引擎/低层系统**：数据导向（热路径内存布局/缓存友好、帧内高频路径免复制）；命令录制与提交分离（录制无副作用、提交点显式可合并）；状态所有权唯一（资源状态由持有者负责转换）；生命周期显式（GPU 对象帧延迟释放，禁止销毁在飞资源）；可观测性内建（计时/计数/validation 计数作为第一公民）；平台差异收敛到 RHI 边界（Vulkan/D3D 差异关在 RHI 实现内）。
- **E. 评审/演进实践**：依赖方向门禁化（纪律落成可执行断言）；文档与代码同步（涉及 CLAUDE.md/AGENTS.md 的变更同一提交更新）；每次改动可回滚（Slice 独立可提交、可回滚）；度量先于优化（无基线不优化）；以 HEAD 为准（Diff 基线是提交而非工作区）。
- **F. 检索手段**：代码检索与符号核验**必须**使用 codegraph CLI（见审查运行时规范「2. codegraph 代码检索约定」），`grep`/`read` 仅用于字面量文本或已定位文件内的就近查看；未建索引的项目先 `codegraph init <项目路径>` 再查，不因"未索引"退回 grep。

### 3.2 审查建议的执行纪律（跨项目默认）

对任何审查（`reviewer` 角色 / 模型 / 人工）给出的建议，**禁止无脑照单执行**，必须逐条核对、确认真有问题后再动手：

1. **逐条核验**：每条建议对照实际源代码逐符号核验（对齐审查运行时规范「十维审查清单」第 3 条），确认问题真实存在才采纳；不凭审查文本本身判定成立。
2. **分级处理**：
   - 确认为真 → 采纳并修正，修正走[补丁交付规范「3. 交付流程」](../patch-delivery/standard.md)的验证与 Diff 交付流程；
   - 误报 / 与实际代码不符 / 前提错误 → 不采纳，并写明核验依据（文件 + 行号 + 实际状况）；
   - 存疑 → 列出不确定点，请用户裁决或补充信息，不自行脑补执行。
3. **冲突时**：多条建议互相矛盾、或与用户既定架构 / 约定冲突时，先报告冲突点与两难，不擅自选边执行。
4. **裁决优先级**：用户明确拍板 > 真问题才改；用户未表态时，默认"有疑问就不改"。

### 3.3 审查-修复闭环（跨项目默认）

适用场景：审查报告产出后，需要将审查意见转化为实际代码修复的场景。

1. **修复采纳**：对于确认为真（🔴/🟡 级）的问题，必须将审查意见**反馈给原代码生成模型**，让其据此生成修复后的 Diff。修复指令中应附上审查报告原文或摘要，确保生成模型能准确理解问题所在。**修复 Diff 的生成必须使用 `task` 角色；审查角色（`reviewer`）只负责审查并给出意见，不参与修复代码生成与修复验证。**
2. **修复验证**：生成的修复 Diff 需重新经过[补丁交付规范「3. 交付流程」](../patch-delivery/standard.md)第 2–5 步（选场地 → 编译 → 回退 → 重新生成 raw patch）。
3. **二次审查（默认聚焦增量）**：复审只做三件事——①逐条核对上一轮 findings（resolved/unresolved/changed + 证据）；②审修复 delta 的 hunk；③对 delta 触及的每个符号做一次 codegraph `impact`/`callers`，确认调用方未被破坏。**升级全量的条件**（自动，附原因）：首轮；delta 缺失或未覆盖 `filesChanged`；变更符号 >6；实现者声明改了公共签名/共享布局/默认行为（`contractChanged`）；改动越出上一轮 findings 文件集合且未给 `scopeNote`；上一轮 review 结果缺失。批处理 `slice` 的复审仍全量。模型档位按本文「2.3 审查模型分层」。
4. **闭环退出条件**：
   - 所有 🔴 级问题已被解决（修复 patch 验证通过）；
   - 🟡 级问题有明确的"已修复"或"接受理由"记录；但[补丁交付规范「2. 最终 patch 的代码放置与 include 顺序」](../patch-delivery/standard.md)属用户硬要求，其条目不得以"接受理由"关闭，须修正或由用户明确豁免；`category: "over-fix"` 与 `category: "slice-leak"` 的条目同样不得以"接受理由"关闭，须最小化修复或由用户明确豁免；
   - 二次审查未发现新的 🔴 级问题；
   - 满足以上条件后，闭环结束，输出最终 `<任务名>.patch` + 薄文档，并生成人工终审摘要（见本文「2.2 审查顺序」第 4 步）。
5. **闭环记录**：审查报告 → 修复 patch → 验证结果 → 二次审查结论，记录在 `AIOut/<任务名>/reviews/<任务名>-fix-loop.md`。单轮修复写摘要；多轮写每轮变更与决策依据。**旧版 patch / 旧文档移入 `archive/`，不在活文档追加附录。**
6. **状态同步**：闭环结束时同步主计划决策日志、Slice 状态、INDEX/版本号（[补丁交付规范「3. 交付流程」](../patch-delivery/standard.md)第 8 步）。
7. **例外**：用户明确表示"仅审查不改"时，跳过本闭环流程，只输出审查报告。
